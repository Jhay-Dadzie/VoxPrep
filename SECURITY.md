# Security Policy

VoxPrep handles credentials, voice recordings, transcripts, and CVs — some of
the most sensitive material a person will hand to an application. This document
describes what is supported, how to report a vulnerability, and the security
properties the system is designed to hold.

## Supported versions

| Version | Supported |
| --- | --- |
| `main` (latest) | ✅ |
| Tagged releases prior to the latest | ❌ |

The project has not yet cut a supported release line. Until it does, only the
current `main` branch receives security fixes.

## Reporting a vulnerability

**Do not open a public issue, pull request, or discussion for a security
vulnerability.** Public disclosure before a fix exists puts every user at risk.

Report privately using one of these, in order of preference:

1. **GitHub private vulnerability reporting** — the *Security* tab → *Report a
   vulnerability*. This is the preferred channel because it creates a private
   thread with the maintainers and an advisory draft in one step.
2. **Direct contact with a maintainer**, if private reporting is not enabled on
   the repository.

> **Maintainers:** enable GitHub private vulnerability reporting and publish a
> monitored security contact address here before making this repository public.

### What to include

- The component affected (API, client, database policy, voice gateway).
- A description of the vulnerability and the impact you believe it has.
- Reproduction steps, or a proof of concept, precise enough for us to confirm it.
- Any suggested remediation.
- Whether you intend to disclose publicly, and on what timeline.

**Redact all credentials from your report.** If a reproduction requires an
access token, describe how to obtain one rather than pasting a live one.

### What to expect

| Stage | Target |
| --- | --- |
| Acknowledgement of your report | 3 business days |
| Initial assessment and severity triage | 10 business days |
| Fix or documented mitigation for high-severity issues | 30 days from triage |
| Public advisory | After a fix ships, coordinated with you |

We follow coordinated disclosure. We will credit you in the advisory unless you
ask us not to. We ask that you give us a reasonable opportunity to remediate
before disclosing publicly.

### Scope

**In scope:** the API in `backend/`, the client in `frontend/`, the SQL schema
and migrations, the voice WebSocket gateway, and this repository's
configuration and documentation.

**Out of scope:** vulnerabilities in Supabase, Google Gemini, or Deepgram
themselves — report those to the respective vendor. Also out of scope: findings
that require a compromised device, a compromised Supabase project, or physical
access; missing hardening headers with no demonstrated impact; and reports
generated by automated scanners without a working proof of concept.

## Security model

### Authentication and authorization

- Authentication is delegated to **Supabase Auth**. The API validates the
  bearer access token on every protected route via the `protect` middleware.
- The client stores tokens in device secure storage (`lib/token-storage.ts`)
  and refreshes them transparently. A refresh failure that is a *network*
  failure does not sign the user out — only a rejected refresh token does.
- **Authorization is enforced in the service layer** with explicit `user_id`
  filters. Row-level security in PostgreSQL is defence in depth, because most
  reads use the service-role client, which bypasses RLS by design.
- Every user-data table has RLS enabled with own-row policies. These are what
  stand between a user and someone else's data if the anon key is ever used
  directly.

### The voice WebSocket gateway

- The socket opens **unauthenticated and mute**. The first frame must be a
  JSON `start` message carrying the access token; anything else is closed with
  `4401`. A connection that sends nothing within 10 seconds is dropped.
- The token is **not** placed in the URL query string. Query strings land in
  access logs, proxy logs, and crash reports, and a Supabase access token in a
  log file is a live credential.
- Loading the session context is also the ownership check — it throws for a
  session belonging to someone else, so there is no separate authorization step
  to forget.
- Frames are capped at 1 MiB (`maxPayload`), and the upgrade handler serves only
  `/api/v1/interviews/agent`.

### Data handling

- **CV text is never persisted.** The `tailored_cvs` table stores the rewritten
  document, the source file name, and the source character count — not the
  extracted text. It is the most sensitive material this feature touches and
  nothing downstream needs it once the model has read it.
- **Uploaded documents are held in memory only** for the duration of the
  request, long enough to extract text, and are then discarded. They are never
  written to disk.
- **Marking schemes are withheld structurally.** A paper being sat is mapped
  through a shape that has no field for the correct option or explanation — a
  stronger guarantee than remembering to delete them.
- Audio for asynchronous transcription may be stored in Supabase Storage under
  a user-scoped path; the live voice interview streams audio and does not
  persist it.

### Transport and headers

- `helmet()` sets standard security headers on every response.
- CORS is allowlisted from `CORS_ORIGIN`. Loopback and private-LAN origins are
  additionally accepted **only when `NODE_ENV !== 'production'`**, so a new DHCP
  lease on a development machine does not require an allowlist edit. In
  production, only the configured origins are accepted.
- Requests without an `Origin` header (native mobile clients, curl) are allowed;
  they are not subject to the browser same-origin model.
- Production deployments **MUST** terminate TLS in front of the API. Access
  tokens and voice audio must never cross the network in clear text.

### Error handling

Errors that name their own status code say something deliberate about what the
client should do, so their message is passed through. Anything reaching the
global handler without a status is an unanticipated fault, and its message is
an internal detail — it is replaced with one flat line and the real text goes to
the log. Stack traces are returned **only** when `NODE_ENV === 'development'`.

### Rate limiting

`express-rate-limit` guards the sensitive auth paths: sign-up, login, and all
password operations each have their own limiter.

## Operator responsibilities

If you deploy VoxPrep, you are responsible for:

- Setting `NODE_ENV=production`. Several protections — the permissive local
  CORS pattern, stack traces in responses, verbose cookies — key off it.
- Setting `CORS_ORIGIN` to your real origins. Leaving it unset in production
  means only requests without an `Origin` header are accepted.
- Keeping `SUPABASE_SECRET_KEY` server-side only. It bypasses row-level
  security. It **MUST NOT** appear in the client, in `EXPO_PUBLIC_*` variables,
  in logs, or in any build artefact shipped to a device.
- Rotating provider keys (Supabase, Gemini, Deepgram) on any suspicion of
  exposure, and after any contributor with access departs.
- Enforcing HTTPS/WSS, and configuring your reverse proxy to allow WebSocket
  upgrades on `/api/v1/interviews/agent`.
- Retention and deletion. `DELETE /api/v1/users/me` cascades a user's data;
  confirm your Supabase Storage lifecycle policy removes stored audio too.

## Known limitations

These are accepted, documented positions rather than undiscovered issues.
Reports restating them will be closed with a pointer here.

- **Uploads have no size ceiling.** Any figure tested turned away ordinary
  course material — a slide deck carrying its images is several times the size
  of the same content as a PDF. The bytes live in memory only for the length of
  the request. Operators who need a limit should impose one at the reverse proxy.
- **Deactivating an account does not invalidate the outstanding JWT.**
  `PATCH /users/me/status` sets a flag; the client must also call
  `POST /auth/logout`. The token remains valid until it expires.
- **Android voice sessions run half-duplex.** The microphone is muted while the
  interviewer is speaking, because Android exposes no equivalent of iOS voice
  processing here. This is a product trade-off, not a vulnerability.
